- **minor** nimbalyst-local/tools/slugify.sh:7 (die() helper) and self_check() lines 21,24,27,30,39,42,45: die() is defined to match agent-context.sh:8 style but is never called anywhere in the script — there is no invalid-usage/argument-rejection path in slugify.sh (unlike word-count.sh, which rejects multi-file args via die). Separately, self_check()'s assertions use `actual=$(printf ... | "$0")` / `actual=$("$0" ...)` unguarded under `set -euo pipefail`. If a future change ever makes slugify() or the arg-parsing path exit non-zero for some input, that command substitution failure trips `set -e` and aborts the whole self-check silently (bare exit 1, no `FAIL:` line printed) instead of reaching the `fail()` call — same pattern already present in the existing word-count.sh, so it is repo-consistent, but it means the self-check's own diagnostic promise ("exit non-zero on first failure" via FAIL:) is not actually guaranteed to print a FAIL: message in that scenario. Confirmed today's slugify() never fails for any input (tested \xff\xfe\x00, \x80\x81\x82, emoji, multibyte UTF-8) so this is not currently reachable — purely a latent/forward-looking gap.
  needed tests: No test currently needed since not reachable; if slugify() ever gains a code path that can exit non-zero, add a self-check assertion for that path and confirm it still prints FAIL: before exiting (e.g. wrap the assertion command substitution with `|| true` and check both exit status and output explicitly, mirroring smoke-test.sh:44's `&& exit 1 || true` guard pattern already established in this repo's conventions doc).

## Subtask word-count-sh

- **minor** nimbalyst-local/tools/word-count.sh:37-43 (self_check) vs line 9 (top-level trap cleanup_input EXIT): self_check() sets `trap cleanup_self_check EXIT` at line 43, which replaces (does not stack with) the top-level `trap cleanup_input EXIT` set at line 9. Currently harmless only because control flow guarantees `--self-check` exits (line 96 `exit 0`) before any code path that could set `input_file` in the same process — self_check's own file reads all go through child `"$0"` invocations in separate processes. But this is fragile: if a future edit reorders logic so self_check runs after `run()` has populated `input_file` in the same process, the stdin tempfile cleanup silently stops firing and a tempfile leaks in $TMPDIR on every invocation. No test currently exercises trap-stacking, so a regression here would go undetected.
  needed tests: Add a regression test (or a code comment) asserting/documenting that self_check and stdin-consuming run() paths are mutually exclusive within a process, OR replace the second `trap ... EXIT` with a combined cleanup function that calls both cleanup_input and cleanup_self_check so the code is robust to reordering.
- **minor** nimbalyst-local/tools/word-count.sh:16-19 (count()) and run()/wc invocation generally: Not exploitable in current tests, but noting for reviewers: `count()` runs `wc "$mode" -- "$1"` inside `raw=$(...)` under `set -euo pipefail`. If `wc` is ever missing/broken on a host (PATH tampering, minimal container image), the command substitution failure correctly triggers `set -e` and the script dies with bash's untrapped-error message rather than the script's own `die()` wrapper, producing an inconsistent (non-'word-count.sh: ...' prefixed) error format compared to every other failure path in this script. Low real-world likelihood (wc is POSIX-mandated) but inconsistent with the die() convention the rest of the script follows.
  needed tests: None strictly required (out of scope per spec, which doesn't mention wc-missing handling), but could wrap the wc call with `|| die 'wc failed'` for consistent error formatting if that convention matters to the codebase.
- **minor** nimbalyst-local/tools/word-count.sh:28-30 (run(), file existence/readability check) vs spec wording 'missing/unreadable file -> die': `[ ! -f "$file" ] || [ ! -r "$file" ]` rejects any non-regular-file path (FIFO, device node, socket) with the same 'cannot read file' message even when such a file might be perfectly readable (e.g., `mkfifo p; producer > p & word-count.sh p` fails, verified by running this exact repro — a live FIFO with data written was rejected). Spec text only says 'missing/unreadable file', which is ambiguous on whether non-regular-but-readable inputs should be supported (stdin already covers the common '-' case, so this is arguably fine, but the exact wording 'unreadable' could be read as implying a readability check via `-r` alone, not `-f`).
  needed tests: If FIFO/special-file support is in scope, add a self-check case for a named pipe input and relax the check to `[ -e "$file" ] && [ -r "$file" ] && [ ! -d "$file" ]`. If out of scope (most likely, given spec says 'file argument'), no test needed — but worth a one-line doc comment noting only regular files are accepted, directories/FIFOs/devices are treated as 'cannot read'.
