## Subtask slugify-sh

- **critical** nimbalyst-local/tools/slugify.sh:11 (slugify()) — sed 's/[^a-z0-9][^a-z0-9]*/-/g' operating on multi-line pattern space: Any input containing an embedded newline byte produces multi-line output, violating the explicit subtask requirement 'output exactly one line with trailing newline'. Repro: `printf 'foo\nbar' | ./slugify.sh` → prints `foo\nbar` (2 lines), completely unslugified around the newline, instead of the expected single line `foo-bar`. Root cause: sed's `s///` never sees the newline as part of the pattern space (it's the line separator), so `[^a-z0-9]` never matches it and it passes through raw. This is not an exotic case — any multi-line file content or copy-pasted multi-line string piped to this tool (its primary stdin use case) triggers it. Reproduced 4/5 times with 500 random bytes via /dev/urandom (lines=5,4,3,4), and deterministically with `printf 'foo\nbar'` via both stdin and a single quoted argv arg (`./slugify.sh 'foo\nbar'`).
  needed tests: Add a self-check case with embedded newline in stdin (e.g. `printf 'foo\nbar\n'`) and in a single argv arg, asserting output is one line `foo-bar` and `wc -l` of the output equals 1. Fix: replace sed line-mode approach with `tr` to first fold newlines/tabs into a placeholder before the sed pass, or use `tr -s` for all non-alnum classes into `-` directly (e.g. `tr -c 'a-z0-9' '-' | tr -s '-' | sed 's/^-*//; s/-*$//'`), which is newline-safe since tr operates byte-wise regardless of line structure.

- **minor** nimbalyst-local/tools/slugify.sh:20-42 (self_check) — SC2015 pattern `A && B || C`: Every assertion uses `[ cond ] && pass '...' || fail '...'`. This is the classic non-if/then/else anti-pattern: if `pass` itself failed (nonzero exit), `fail` would also run. Here pass() only does printf so it can't fail in practice, so this is currently benign, but it's a latent footgun if pass() is ever extended (e.g. to increment a counter via arithmetic `((n++))` which returns nonzero when n was 0) — a future edit could cause double PASS+FAIL output or mask failures. shellcheck flags this as SC2015 on all 8 assertion lines.
  needed tests: No new test needed now; if pass()/fail() are ever extended, switch to explicit `if [ cond ]; then pass ...; else fail ...; fi` to avoid the anti-pattern silently breaking semantics.
