# task-orchestrator 신뢰성·부하 평가

측정일: 2026-09-09. 판정: **조건부 적합 — 로컬 사용 범위의 상태 무결성은 양호, 작업 300개 누적 시 시작 지연 목표 초과.**

## 범위와 사전 기준

대상은 구현된 `task_state.py`의 상태 저장·전이·CLI이다. 실제 LLM 판단 품질, 모델 비용, Claude/Codex 전체 팀 실행 및 브라우저 E2E 신뢰도 점수는 아니다. 구현 코드는 수정하지 않고 테스트와 보고서만 추가했다.

- 무결성: 중복 ID, 유실된 갱신, 잘못 승인된 충돌, 손상된 권위 상태 0건.
- 성능: 각 측정 조건에서 p95 ≤ 2,000ms, 예상 밖 CLI 오류 0건.
- 위 성능 기준은 실행 전에 정한 **로컬 사용용 임시 목표**이며 사용자 합의 운영 SLA가 아니다.
- 관측 통과율 100%는 실제 운영 무고장률 100%를 의미하지 않는다. 임의 가중치의 종합 점수 대신 항목별 수치와 실패 조건으로 판정했다.

## 환경·측정 방법

- macOS 26.5.2 / arm64, 논리 CPU 10개, RAM 16GiB, Python 3.14.5.
- 대상 파일 SHA-256: `fb172615983ac2a926e0be1681c5ff5e5188c2a2ddd4781ac3629d94fb4ad749`.
- 격리된 임시 Git 저장소, 실제 Python CLI 프로세스. Python 시작·JSON 출력·디스크 기록·잠금 대기 시간을 포함한다.
- 클라이언트마다 한 요청 완료 후 다음 요청을 보내는 closed-loop 방식. 외부 대기열은 측정하지 않았으므로 포화 부하 SLA로 해석하면 안 된다.
- OS 캐시를 비우지 않은 로컬 측정이며 전용 벤치마크 장비가 아니다. 성능 실행 중 회귀/신뢰성 전체 스위트는 겹치지 않게 했다.
- p95는 nearest-rank. 처리량은 성공 요청 수 / 해당 조건 전체 경과 시간이다. 부하 조건당 96회, 파일/이력 조건당 30회, 작업 누적 조건당 10회 측정했다. 마지막 조건의 p95는 표본 최대값과 같아 정밀한 꼬리 지연 추정은 아니다.

## 회귀 신뢰성

기존 20개 테스트를 최초 1회 통과한 뒤 추가 10회 반복했다. 반복 결과 **200/200 통과**, 실패 실행 **0/10**, 반복 총 41.6초. 같은 고정 스위트 반복이므로 독립적인 운영 사건 200건으로 해석하지 않는다.

범위: 현재 기준·코드·증거 검증, HIL 승인, UI 필수 게이트, 연구 결과 무효화, DAG 의존성, 소유권 경합, 시도 ID 유지, 이슈 재배정, 완료 보고서 저장 실패 등.

원시 로그: [regression-repeated.json](regression-repeated.json).

## 동시성·장애 주입 신뢰성

독립적으로 작성한 추가 시험을 실행한 결과 **6/6 검사 그룹 통과**, 실행 시간 24.0초다. 의도된 충돌 거절은 오류율에 넣지 않고, 예상한 수만큼 거절됐는지를 검증했다.

| 검사 | 실행량 | 관측 결과 | 판정 |
| --- | --- | --- | --- |
| 병렬 task ID 할당 | 16클라이언트, 64요청 | 고유 ID 64개, 중복/실패 0건 | 통과 |
| 같은 revision 쓰기 경합 | 32요청 × 10회 | 매회 1건만 반영, 나머지 310건 거절; 이력 유실 0건 | 통과 |
| 같은 파일 소유권 경합 | 2요청 × 10회 | 매회 실행 1건/거절 1건; 중복 실행 0건 | 통과 |
| workspace 실행 상한 | 8요청 × 10회 | 매회 4건 실행/4건 거절; 상한 초과 0건 | 통과 |
| 보고서/상태 저장 경계 강제 종료 | 4개 지점 각 1회 | 예상 종료 코드 4/4, 미반영 상태 전체 보존 3/3, 재개 완료 3/3 | 통과, 아래 주의 |
| 보고서 쓰기 오류 | 1회 | CLI 오류 반환, revision 9·reporting 유지 | 통과 |

동시성 경합 420요청 중 예상한 60건만 반영되고 나머지 **360/360건이 정확히 거절**됐다.

### 확인된 일관성 주의점

강제 종료는 `os.replace` 전후에서 `os._exit`를 호출한 결정적 장애 주입이다. 실제 전원 차단 시험은 아니다.

| 종료 지점 | 직후 state.json | 직후 report.md | 재개 |
| --- | --- | --- | --- |
| 보고서 교체 직전 | reporting / revision 9, 전체 상태 보존 | 없음 | 완료 / revision 10 |
| 보고서 교체 직후 | reporting / revision 9, 전체 상태 보존 | completed / revision 10 | 완료 / revision 10 |
| 상태 교체 직전 | reporting / revision 9, 전체 상태 보존 | completed / revision 10 | 완료 / revision 10 |
| 상태 교체 직후 | completed / revision 10 | completed / revision 10 | 이미 일치 |

**두 파일은 하나의 원자적 트랜잭션이 아니다.** 4개 주입 지점 중 2개에서 보고서가 상태보다 앞섰다. 이는 발생 확률 50%라는 뜻이 아니라 선택한 경계에서의 재현 결과다. `report.md`만 읽어 완료로 판정하면 안 되며, `show`의 권위 상태와 revision을 확인해야 한다. 미반영 상태 3개는 현재 revision으로 완료 이벤트를 다시 적용해 3/3 복구했고 보고서 revision도 일치했다. 마지막 지점은 프로세스 종료 코드가 비정상이더라도 저장 자체는 완료됐으므로 무조건 재실행하지 않는다.

원시 결과: [reliability.json](reliability.json).

## CLI 부하

읽기는 `show`, 쓰기는 다른 task별 `criteria` 이벤트 갱신이다. 16개 클라이언트는 CLI 요청 동시성이지 개발자 에이전트 16개 실행이 아니다. 개발 작업 상한은 별도 4개다.

| 작업 | 동시 클라이언트 | 요청 수 | p50 ms | p95 ms | 최대 ms | 성공 요청/초 | 오류 | 상태 무결성 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| show | 1 | 96 | 55.6 | 59.3 | 63.6 | 18.0 | 0 | 통과 |
| show | 4 | 96 | 65.1 | 76.4 | 82.4 | 60.3 | 0 | 통과 |
| show | 8 | 96 | 95.0 | 126.3 | 129.3 | 79.3 | 0 | 통과 |
| show | 16 | 96 | 182.2 | 283.6 | 341.3 | 78.5 | 0 | 통과 |
| apply | 1 | 96 | 75.3 | 80.9 | 84.0 | 13.3 | 0 | 통과 |
| apply | 4 | 96 | 88.9 | 109.7 | 121.8 | 43.7 | 0 | 통과 |
| apply | 8 | 96 | 132.3 | 161.1 | 195.3 | 58.2 | 0 | 통과 |
| apply | 16 | 96 | 263.3 | 353.6 | 448.9 | 57.5 | 0 | 통과 |

총 **768/768 요청 성공**, revision/이력 연속성 불일치 **0건**. 읽기 8→16클라이언트에서 처리량 79.3→78.5회/초, 쓰기 58.2→57.5회/초로 추가 병렬화 이득은 관측되지 않았다.

## 크기별 부하

| 조건 | 표본 수 | p95 ms | 판정 |
| --- | ---: | ---: | --- |
| 파일 100개 × 4KiB 스냅샷 | 30 | 93.7 | 통과 |
| 파일 1,000개 × 4KiB 스냅샷 | 30 | 144.9 | 통과 |
| 파일 5,000개 × 4KiB 스냅샷 | 30 | 361.1 | 통과 |
| 이력 10개 상태 갱신 | 30 | 80.8 | 통과 |
| 이력 1,000개 상태 갱신 | 30 | 96.8 | 통과 |
| 이력 10,000개 상태 갱신 | 30 | 181.0 | 통과 |
| 같은 workspace 작업 1개에서 start | 10 | 84.8 | 통과 |
| 같은 workspace 작업 100개에서 start | 10 | 1030.3 | 통과 |
| 같은 workspace 작업 300개에서 start | 10 | 2989.4 | **실패** |

이력 크기 시험은 합성 이력으로 10/1,000/10,000개를 미리 채운 뒤 실제 CLI 갱신을 측정했다. 10,000개 초기 상태는 5,219,385 bytes다. 작업 누적 시험은 실제 생성한 비실행 task 0/99/299개와 대상 task 1개로 구성했다. 스냅샷은 최대 5,000파일·20,480,000 bytes이며 동일 입력의 fingerprint 불일치는 없었다.

**실패 원인:** [start 구현](../../../.claude/skills/task-orchestrator/scripts/task_state.py)의 345행부터 시작할 때마다 같은 workspace의 다른 task를 전부 읽고, 각 `load`에서 Git root를 다시 확인한다. 관측 p95는 1개 84.8ms → 100개 1,030.3ms → 300개 2,989.4ms. 300개에서는 목표보다 49.5% 느리고, workspace 잠금을 잡은 상태라 다른 쓰기 대기도 길어질 수 있다. 후자는 코드 구조에 근거한 영향 예상이며 300개 상태의 동시 쓰기는 별도 측정하지 않았다.

성능 조건은 **16/17 통과**, 300개 task의 시작 지연 조건 1개 실패. 해당 실패를 드러내도록 벤치마크 종료 코드는 1이다. 수정 전 재현 결과를 보존했다.

원시 측정값: [load.json](load.json).

## 적용 판단과 한계

- 이번에 측정한 일반 상태 갱신·5,000파일·10,000이력 범위는 임시 지연 목표를 만족했다.
- 작업 누적 100개에서는 시작 p95 약 1초, 300개에서는 약 3초다. **현재 버전을 누적 작업 수가 큰 workspace에 무조건 적합하다고 볼 수 없다.**
- 개선 우선순위는 누적 task 전체 스캔과 반복 Git 조회 축소다. 이번 요청은 평가이므로 구현 변경·데이터 정리·아카이빙은 실행하지 않았다.
- 장시간 soak, 프로세스 CPU/RSS, 디스크 고갈, 실제 전원 차단, 네트워크 파일시스템, 외부 모델/브라우저 통합은 미측정이다.
- 완료 보고서를 단독으로 소비하는 자동화는 위 저장 경계 문제 때문에 부적합하다. `state.json` 기준으로 판정하는 계약을 지켜야 한다.
- UI가 없는 CLI 구현이므로 실제 화면 시험은 not-applicable; UI 필수 여부를 강제하는 상태 게이트는 회귀 테스트로만 검증했다.
- 별도 lint/typecheck 도구는 이 구현용으로 발견되지 않았다. AST 문법 검사를 실행했으며 이를 lint/typecheck 통과로 대체하지 않았다. 기존 hook/evolve 스위트는 이번 구현과 무관하며 글로벌 스킬·세션 상태를 정리하므로 실행하지 않았다.

## 변경·부작용

추가 파일은 부하/신뢰성 러너 2개와 이 디렉터리의 보고서·원시 JSON 4개다. 기존 구현 파일 SHA-256은 측정 전후 동일함을 확인했다. 테스트 대상은 임시 저장소만 사용했고, 런타임 스킬 상태·글로벌 스킬·의존성·설정은 변경하지 않았다. 검사 과정의 Python 캐시는 제거했으며 기존 미커밋 변경은 보존했다.
